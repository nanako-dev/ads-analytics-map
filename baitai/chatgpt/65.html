1-1.運用の判断への効き方

  • Claude Code（ads-mcp）からつなぐなら、Advertiser API ＋ API キーが今すぐ使える唯一の道。パートナーの OAuth は読み取りだけに絞れて理想的だが、自分で登録する手順が公開されていない ?
  • ChatGPT の中から見るだけなら、プラグインが一番手軽。ただし Claude からは使えない。両方を並べて使うなら、プラグインの「直近 7 日」の既定と、こちらの道具の期間をそろえる
  • 外部のデータ連携サービスにキーを渡すのは、運用の原則 5（鍵を AI に渡さない、手元のファイルに置く）と、キーが書き込みもできる点から勧めない〔推測〕

2.「自分の広告アカウントの日次の実績を読むだけ」に要る最小の準備

この節の要点
  • 要らないもの
  • Google のような段階（エクスプローラー・ベーシック）も無い
  • 自分の役割を確かめる
  • キーを作る
  • 名前を付けても権限は絞れない
  • キーをその場で手元のファイルに保存する

要らないもの（公開の文書に出てこない）: 開発者の登録、アプリの作成・審査、利用の申請、Cloud プロジェクト、OAuth の同意画面、利用料（記載なし ?）。Google のような段階（エクスプローラー・ベーシック）も無い ✓公式S-01（Getting Started は「広告アカウントと Advertiser API キーが要る」だけ）

2-1.手順（番号順。AI はどれも代わりにしない）

  1. 1
    自分の役割を確かめる

    Ads Manager の「設定 > ユーザー」で、自分がその広告アカウントの管理者（Admin）か見る。パートナーの手順は「キーを作る前に管理者の権限があることを確かめる」と書く ✓公式S-62（Fospha の項）。メンバー・閲覧者でキーを作れるかは ?

    • 役割は広告アカウントごとに 管理者／メンバー／閲覧者。閲覧者は書き込みも管理もできない。ChatGPT のワークスペースや API Platform の組織の役割は、広告の権限にならない ✓公式S-40（本文）、S-39
  2. 2
    キーを作る

    「設定 > 一般 > API キー」→「Create New Key」（新しいキーを作成）✓公式S-62、〔画面〕62 #16。名前は用途が分かるもの（例: 「ochinana-ads-mcp 読み取り用」）。名前を付けても権限は絞れない〔推測: A-01 の入力は名前だけ〕

    • 画面に権限・期限を選ぶ欄があれば、読み取りだけ・短い期限を選ぶ（欄があるかは ?。あれば 62 に記録する）
  3. 3
    キーをその場で手元のファイルに保存する

    例 ~/.config/ochinana-ads/openai-ads.key（中身はキー 1 行だけ）。chmod 600 で自分だけが読めるようにする。チャットに貼らない、ads-mcp のフォルダや git の中に置かない（運用の原則 5）。キーが作成時に 1 回しか表示されないかは ?（第三者の解説はそう書く）

    • 公式も「サーバーに安全に保存する」「秘密の管理の仕組みに置き、ブラウザのコード・ログ・ソース管理に入れない」と書く ✓公式S-01（Getting Started、Conversion Setup）
  4. 4
    1 回だけ動作を確かめる

    bash curl -sS -G "https://api.ads.openai.com/v1/ad_account" -H "Authorization: Bearer $(cat ~/.config/ochinana-ads/openai-ads.key)" ` 返ってきた id（adacct_…）・timezone（Asia/Tokyo のはず）・currency_code（JPY のはず）・status・review` を見る。公式も最初にこれで確かめると書く ✓公式S-01。この呼び出しは読むだけで、広告費はかからない

  5. 5
    Claude に渡すのは 2 つだけ

    キーのファイルの場所と、広告アカウントの id（許可リストに入れる）。キーの中身は渡さない

  6. 6
    もう 1 つのアカウントも読むなら

    そのアカウントに切り替えて 1〜5 を繰り返す（キーはアカウントごと）✓公式S-01

  7. 7
    止めるとき・漏れたとき

    「設定 > 一般 > API キー」で消す〔推測〕。削除・失効の手順と、キーの期限・本数の上限は公開の文書に無い ?

2-2.間違えやすい点

  • コンバージョン API キーは別物。計測の「コンバージョン」の画面か API で作るキーで、サーバーから成果を送るためだけのもの。送り先も別（bzr.openai.com）。レポートの読み取りには使わない ✓公式S-01（Conversion Setup、Troubleshooting の API Errors）
  • ChatGPT や API Platform（platform.openai.com）のキーでは呼べない〔第三者: 検索結果の解説。公式の明文は ?〕。公式は「Ads API キーは 1 つの広告アカウントに紐づく」とだけ書く
  • 請求の上限（アカウントの支出の上限）の API は、読むだけでも「請求を管理する権限」が要る ✓公式S-01（Account spending limits）。日次のシートには使わない

2-3.運用の判断への効き方

  • 準備は 10 分ほどの手作業で終わる〔推測〕。Google のような審査待ちは無い
  • いちばんの危険はキーが書き込みもできること〔推測〕。だから、①管理者がキーを作るが、②キーを使う道具は読むだけの呼び出ししか持たない（§6）、③漏れたらすぐ消す、の 3 点で守る

3.日次の実績を取る呼び出し

この節の要点
  • POST だが読むだけ
  • API キーでだけ呼べる
  • until を含む

6-1.読むだけに絞れるか

  • キーそのものは絞れない（§0）。だから道具のコードで絞る。Google の版と同じく「アカウントを変える呼び出しはコードのどこにも無い」をテストで確かめる
    • 呼んでよい端点の許可リスト: GET /v1/ad_account、GET /v1/campaigns・/v1/ad_groups・/v1/ads（一覧と取得、include[]=serving_issues）、GET /v1/ad_account/insights とキャンペーン・広告グループ・広告の Insights、GET /v1/audit_logs、GET /v1/ads/{ad_id}/landing_page_crawl（審査のクローラーが LP を取った記録。読むだけで、新しく取りには行かない。画面の写しの URL は最長 24 時間 ✓公式A-01）、そして POST は POST /v1/conversions/insights の 1 本だけ（読むだけの POST）
    • それ以外の POST・PATCH・DELETE（/activate・/pause・/archive・/api_keys・/upload など）は、送る前に道具が断る。テストで「許可リスト外の道を組み立てられない」ことを確かめる
  • 将来、パートナーの OAuth（読み取りの ads.admin.all.read）を個人でも使えるようになれば、鍵の側でも読むだけにできる。今は登録の手順が公開されていない ?

  • 日次のシートのスクリプトは、上の chatgpt_get_performance（キャンペーン × 日、費用などは直近 3 日・成果は直近 30 日）と chatgpt_get_conversions（同じ範囲の内訳）を毎朝 1 回ずつ呼び、行を「日付 × キャンペーン」で上書きする。窓は「クリック 30・ビュー 0」と「クリック 30・ビュー 1」の 2 列で持つ
  • 呼び出しの数は 1 日数回で、毎分 600 の上限から遠い
